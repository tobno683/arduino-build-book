Your first sketch

Arduino code is C++ with two functions you must write and a large library of helpers. If you have written any JavaScript, Python or Java, you already know 80 % of the syntax. This page covers the other 20 % and every error message you are about to meet.

Getting the IDE working

  1. Install the Arduino IDE

    Get version 2.x from arduino.cc. It has autocomplete, a proper debugger and a sane library manager. (The old 1.8 IDE still works and is lighter if your machine is slow.)

  2. Plug the board in and look for the port

    Tools → Port. Note what is listed, unplug the board, look again. The entry that disappeared is your board. Windows shows COM3-ish, macOS /dev/cu.usbmodem…, Linux /dev/ttyUSB0 or /dev/ttyACM0.

  3. If no port appears

    Almost always one of three things:

    • A charge-only USB cable. Astonishingly common. Try another cable first - it costs ten seconds and solves this more often than anything else.
    • Missing CH340 driver. Nearly every clone uses a CH340 or CH341 USB chip. Search "CH340 driver" plus your OS, install, replug.
    • Linux permissions. sudo usermod -a -G dialout $USER, then log out and back in.

  4. Select the board

    Tools → Board → Arduino Uno (or Nano). For an old Nano clone you may also need Tools → Processor → ATmega328P (Old Bootloader) - if uploads fail with a timeout, try the other option before you conclude anything is broken.

    For ESP32 or ESP8266 you first add a board package: File → Preferences → Additional Board Manager URLs, paste the ESP32 URL, then Tools → Board → Boards Manager and install "esp32".

  5. Upload Blink

    File → Examples → 01.Basics → Blink, then the arrow button. The built-in LED starts flashing once a second. You have now proved the toolchain, the cable, the driver, the port and the bootloader all work - which means every problem after this is yours, and that is progress.

The shape of a sketch

Every Arduino program has exactly two required functions.

There is no main(). The framework supplies one; it calls setup() once and then loop() over and over, for as long as there is power. There is no operating system, no scheduler and nothing else running. If your loop() takes a second, your program does nothing else for that second.

Serial: the only debugging you get

There is no console, no breakpoint by default and no way to see a variable. Serial.println() is how you find out what is happening, and learning to sprinkle it liberally is the single biggest productivity gain available to a beginner.

Open Tools → Serial Monitor and set the baud rate in the bottom-right corner to match the number in Serial.begin(). Mismatched baud is why you get pages of •�•� - it is not a crash, it is the wrong speed.

Serial Plotter

Tools → Serial Plotter graphs any numbers you print, live. Print several space-separated values on one line and you get several traces. For anything involving a sensor that wobbles - accelerometers, light sensors, moisture probes - this turns an invisible problem into an obvious one.

Why delay() ruins everything, and what to use instead

delay(1000) does not mean "wait a second before the next line". It means "do absolutely nothing for a second". No button gets read, no sensor gets sampled, no display updates. One delay() is fine. The moment you want two things happening at different rates, it falls apart.

The subtraction millis() - lastBlink is deliberate, not stylistic. millis() overflows back to zero after about 49 days; written this way the arithmetic still comes out right through the rollover, because it is unsigned. Written as millis() > lastBlink + interval it breaks once, mysteriously, seven weeks in.

Buttons bounce

A mechanical switch does not close cleanly. The contacts chatter for a few milliseconds, and a chip running at 16 MHz sees one press as five or ten. Your counter jumps by four, your menu skips three items, and you conclude the button is faulty.

Types actually matter here

On a desktop you can ignore integer sizes. On a chip with 2 KB of RAM you cannot.

The two classic overflow bugs

int x = 60 * 1000; gives you −5536, because both operands are int and the multiplication happens in 16 bits before it is assigned. Write 60UL * 1000UL.

int start = millis(); throws away the top half of the number and your timing becomes nonsense after 32 seconds. Use unsigned long.

Memory, and the crash with no error message

An Uno has 32 KB of flash for your program, 2 KB of SRAM for variables, and 1 KB of EEPROM that survives power-off. Flash you will rarely fill. SRAM you will.

The IDE tells you after every compile: "Global variables use 1,204 bytes (58%) of dynamic memory". Under 70 % is comfortable. Over 85 % and you will get the signature symptom of running out: the sketch compiles, uploads, runs for a while, then restarts or prints garbage, with no error anywhere.

Three fixes, in order of effectiveness:

  • Serial.println(F("text")) keeps the string in flash instead of copying it into RAM at boot. Every literal string in a sketch costs RAM without this. It is free to use and the single biggest win.
  • Use byte instead of int where the value fits, especially in arrays.
  • Stop using String. Concatenating them repeatedly fragments the small heap until an allocation fails silently.

Every error message you are going to hit

MessageWhat it actually means
'x' was not declared in this scopeTypo, wrong capitalisation (digitalwrite is not digitalWrite), a missing #include, or you declared the variable inside a different pair of braces.
expected ';' before '}' tokenMissing semicolon - and it is on the line above the one reported, almost every time.
expected declaration before '}' tokenOne closing brace too many, or one opening brace too few. Use Ctrl-T to auto-format; the indentation will show you where.

avrdude: stk500_recv(): programmer is not respondingWrong port, wrong board, wrong processor variant, or something is connected to pins 0 and 1. Unplug everything from 0 and 1 and try again - that fixes it surprisingly often.
avrdude: ser_open(): can't open deviceThe Serial Monitor of another window has the port. Close it. Or the board came unplugged.
A fatal error occurred: Failed to connect to ESP32Hold the BOOT button while the upload starts. Some boards need it every time; some need a 10 µF capacitor between EN and GND.
Sketch too bigGenuinely out of flash. Usually a big graphics library or a font.
Low memory available, stability problems may occurA warning, not an error, and it is right. See the memory section above.
It compiles and uploads, then nothing happensNot a code problem. Check power, check wiring, add Serial.println("setup ran") as the first line of setup().

Libraries

A library is somebody else's code that knows how to talk to a specific chip. Using one is not cheating; writing your own DHT22 pulse decoder is a fine afternoon and a terrible use of your first week.

  • Installing: Sketch → Include Library → Manage Libraries, search, Install. Say yes when it offers dependencies.
  • From a ZIP: Sketch → Include Library → Add .ZIP Library. For GitHub libraries that are not in the manager, download the repository as a ZIP and use this.
  • Finding out how to use one: File → Examples, scroll down past the built-ins to the section named after your library. The examples are written by whoever wrote the library and are usually the best documentation that exists.
  • Two libraries with the same name: real and annoying, particularly for DHT and for OLED drivers. If a sketch will not compile against a library you just installed, check you have the one the project actually names.
